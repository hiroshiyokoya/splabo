# AI に渡すドメイン知識

AI に分析コード（SQL / Python）を書かせるときにプロンプトへ埋め込む知識（#575）。

**役割分担**: 使えるビューと列の一覧は `ai_views.rs` の `schema_prompt()` が生成する。このファイルは
**列名からは分からない「意味」**だけを扱う。二重に書かない。

構造で防げるものはビュー側に焼き込んである（引き分けは `won = NULL`、0 除算は NULL、時系列列は
9 時境界で計算済み、味方ブキは重複を畳んで自分を除く、など）。ここに書くのは**焼き込めなかったもの**。

## 値の一覧は DB から確かめられる

ウデマエやシーズンのように、実際に入っている値が環境で違うものは**推測しないで引く**。

```sql
SELECT DISTINCT rank_before FROM ai_battles WHERE rank_before IS NOT NULL;
SELECT DISTINCT season, game_ver FROM ai_env_slots;
```

## A. 集計の規約（間違えると数字が変わる）

### 日付は 9 時境界。**時刻をずらさない**

Splatoon の 1 日はローカル時間の 9:00 から始まる。`played_at` は UTC 保存で、
`UTC 0:00 = JST 9:00` なので**シフトせずに** 9 時境界の日付になる。
`day` / `week` / `month` 列は計算済み。**親切心で `-9 hours` すると 1 日ずれる。**

### 母数が違う指標を混ぜない

| 指標 | 母数 |
|---|---|
| 勝率・ピック率 | 投稿者を除く 7 スロット全員 |
| キル・デス・アシスト・塗り | **記録のあるスロットだけ** |

環境データは再取得前だと **1 人分しか KDA を持たない**。KDA を見る集計では `WHERE has_kda` で絞る。
絞らないと「平均キル」が一部のバトルだけの数字になる。

### 環境データの母数は投稿者を除く 7 人

`ai_env_slots` は投稿者本人（`a1`）を含まない。stat.ink の全体統計と同じ数え方で、自分のバトルだけを
上げる人が多く投稿者のブキと勝敗に偏りが出るため。

ピック率の分母は「バトル数 × 7」。

### `poster_rank` / `poster_power` は投稿者本人の値

その行のプレイヤーのものではない。「ウデマエ帯毎の環境」は正確には
**「その帯の投稿者が遭遇した卓の分布」**。断定的に「S+ 帯のプレイヤーは〜を使う」とは書かない。

### 味方 / 相手ブキの集計は「合計がバトル数を超える」のが正常

`ai_battle_weapon_presence` は 1 バトルが複数行に寄与する（味方 3 人が別ブキなら 3 行）。
**ブキごとのバトル数を足すと実バトル数の 3〜4 倍になる。** これは異常ではない。

同一バトル内の同じブキは 1 行に畳んであり、`ally` からは自分を除いてある。

このビューと `ai_battles` を結合して出す平均系の値は「**そのブキが居たときの自分の戦績**」であって、
そのブキを使った人の戦績ではない。後者を見たいなら `ai_battle_players` を使う。

### プレイヤー行は詳細取得済みのバトルだけ

`ai_battle_players` / `ai_battle_weapon_presence` は、詳細を取得したバトルにしか行が無い。
`ai_battles` と結合すると**黙って母数が減る**。揃えたいときは `WHERE has_players` を使う。

## B. Splatoon のドメイン知識

### ルール

`nawabari` / `area` / `yagura` / `hoko` / `asari`（+ `tricolor`）。

**ナワバリだけ塗り率で勝敗が決まる。** 他 4 つ（ガチルール）はオブジェクトの進行度で決まる。
したがって

- ナワバリでは**塗りポイントの重要度が高く、キルは手段**。キル系指標に強い意味を読み込まない
- ガチルールでは塗りは前提条件で、勝敗との相関は弱くなりやすい

**ルールを混ぜた集計は解釈が難しくなる。** 指標の意味が変わるため、ルールで絞るか、ルール別に出す。

`our_team_percent` / `their_team_percent`（塗り率）は**ナワバリでのみ意味を持つ**。

トリカラマッチは他とルールが大きく異なるため、アプリのバトル一覧では扱っていない。

### ロビー

`regular` / `bankara_open` / `bankara_challenge` / `xmatch` / `splatfest_open` /
`splatfest_challenge` / `event` / `private`。

**ウデマエが動くのはバンカラ、X パワーが動くのは X マッチだけ。** レギュラーやフェスでは
`rank_before` / `x_power_before` は変化しないか入っていない。

バンカラのオープンとチャレンジは別物（チャレンジはウデマエの増減が大きい）。

### ウデマエと X パワー

`rank_before` / `rank_after` は C- から S+ までの文字列（S+ には数値の細分が付く）。
**文字列なので大小比較はできない。** 順序を扱うなら明示的に並び順を与える必要がある。

`x_power_before` / `x_power_after` は X マッチのレート（実数）。

### ギアパワー

3 部位（アタマ / フク / クツ）× メイン 1 + サブ最大 3。`ai_battle_players` に
`head_primary` / `head_sub1..3` の形で **8 人全員分**入っている（相手のギアも見られる）。

- **メイン = 10AP、サブ = 3AP。** 1 部位の最大は 10 + 3×3 = 19AP
- **積算型（stackable）と発動型（main_only）がある。** 発動型（イカニンジャ等）はメイン専用で
  AP を積まない。**AP を合計するのは積算型だけ**
- ビューは AP を計算していない。合計が必要なら上の重みを使って自分で計算する

### バトルの構成

4 対 4 の 8 人。`is_knockout` はノックアウト決着（1）と時間切れ決着（0）の区別。

### ブキ

`weapon_category` はシューター / ローラー / チャージャー等。**リールガンは公式の分類変更に合わせて
シューターに統合してある**（別カテゴリとして出てこない）。

サブ・スペシャルは `sub_weapon` / `special_weapon`。同じブキでもコラボ版はサブ・スペシャルが違う。

## C. 分析の作法

### サンプル数で足切りする

**5 戦のブキが勝率 100% で 1 位になる。** 順位を出すときは必ず下限を設ける。
アプリ内の既定は勝率・ピック率が 50、KDA 系が 20〜30。

件数も一緒に出す。順位だけ出して件数を隠さない。

### 相関を因果として書かない

「デスが多いと負ける」は「負け試合ではデスが増える」とも読める。相関の向きは決められない。
**「〜と相関がある」までにとどめる。**

### 期間を絞る

ゲームのバランス調整（`game_ver`）でブキの強さは変わる。全期間を混ぜた「最強ブキ」は
複数バージョンの平均になる。バージョンかシーズンで絞るか、時系列で見る。

### 0 件・NULL を確認する

絞り込みの結果が 0 件でもクエリは成功する。件数を必ず確認し、0 件なら「該当なし」と答える。
無理に数字を作らない。
